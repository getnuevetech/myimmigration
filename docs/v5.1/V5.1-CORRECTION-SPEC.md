## 5. Core data model requirements

### 5.1 Fact with provenance

Every ledger fact MUST carry explicit provenance. **Production joins on immutable IDs**, not filenames:

```json
{
  "fact_id": "FORM_I360_FILED",
  "status": "VERIFIED",
  "value": true,
  "sources": [
    {
      "source_type": "DOCUMENT",
      "document_id": "doc_…",
      "content_hash": "sha256:…",
      "document_type": "uscis_i360_receipt_notice",
      "extracted_field": "form_number",
      "source_page": 1,
      "source_channel": "CUSTOMER_UPLOAD",
      "issuer": "USCIS",
      "authority_rank": "USCIS_GOVERNMENT_DOCUMENT"
    }
  ],
  "as_of": "ISO-8601"
}
```

`superseded_by` belongs on **current case posture** records (§5.4), not on historical event facts.

Golden fixtures may use friendly `alias_file_name` for readability; the contract requires `document_id` + `content_hash` in production.

Customer “Verified from your documents” MUST be traceable to at least one DOCUMENT source.

**Resolution vs promotion:** Uploading an I-485 receipt **resolves** unknown `I485_RECEIPT` and **promotes** `FORM_I485_FILED` from `REPORTED` → `VERIFIED`. These are distinct operations.

**Marriage granularity:** Model `MARRIAGE_EXISTS` (often verifiable from civil record) separately from `SPOUSE_US_CITIZEN` (often reported until citizenship evidence exists).

### 5.2 Evidence authority hierarchy (highest → lowest)

Authority rank follows **issuer + document type**, not upload channel:

| Rank | Examples |
| --- | --- |
| 1. USCIS / government document | USCIS receipt, prima facie, RFE, approval/denial — even if `source_channel = CUSTOMER_UPLOAD` |
| 2. Filed form / official receipt | Filed packet copies when issuer is the filing record |
| 3. Civil / professional record | State vital records marriage certificate; attorney letter |
| 4. Customer-authored supporting document | Personal declaration |
| 5. Customer statement | Interview answers / free text |
| 6. AI inference | Never alone for verified material facts |

**Independent fields:** `source_channel` (how it arrived) vs `issuer` (who issued) vs `authority_rank` (evidentiary weight). A USCIS approval notice uploaded by the customer is still `USCIS_GOVERNMENT_DOCUMENT`.

When two sources **affirmatively disagree**, create a **CONFLICT** (§5.3). Do not silently pick. Higher authority may win for `VERIFIED` value; lower may remain as `REPORTED` alongside when not contradictory.

### 5.3 Claim taxonomy: CONFLICT / UNVERIFIED_CLAIM / EVIDENCE_GAP

Three distinct conditions (do not collapse):

| Kind | Meaning | Example | Result |
| --- | --- | --- | --- |
| **CONFLICT** | Two sources **affirmatively disagree** | Customer: I-485 approved **vs** USCIS denial notice: denied | Conflict object; WARNING (or BLOCK if pathway-breaking) |
| **UNVERIFIED_CLAIM** | Customer reports something available evidence does **not yet prove** (and does not contradict) | Customer: I-485 approved; USCIS receipt proves filing only; no decision notice | Approval stays `REPORTED` / unverified — **not** a conflict |
| **EVIDENCE_GAP** | Material fact cannot yet be determined | No I-485 receipt or decision available | `UNKNOWN`; action to obtain evidence |

**Forbidden:** `source_b = RECEIPT_ONLY` against `APPROVED`, or an **absent** document as `source_b`. A receipt does not contradict approval.

Genuine conflicts are first-class and connect evidence → action:

```json
{
  "conflict_id": "conf_…",
  "subject": "I485_FINAL_DECISION",
  "source_a": { "type": "USER_STATEMENT", "value": "APPROVED" },
  "source_b": { "type": "USCIS_DOCUMENT", "value": "DENIED", "issuer": "USCIS" },
  "severity": "WARNING",
  "resolution_status": "UNRESOLVED",
  "required_action": "UPLOAD_OR_CONFIRM_CONTROLLING_I485_NOTICE"
}
```

### 5.4 Event timeline vs current-state supersession

**Two models — do not mix:**

**EVENT TIMELINE** (accumulates; events do **not** supersede each other):

`Receipt → Prima facie → RFE → RFE response → Final decision`

The receipt remains historically true after prima facie or approval.

**CURRENT CASE POSTURE** (this is what gets superseded):

`FILED_PENDING → PRIMA_FACIE_PENDING → RFE_PENDING → UNDER_REVIEW → APPROVED|DENIED|WITHDRAWN`

`superseded_by` / `supersedes` apply **only** to posture records.

Use fact id **`I360_FINAL_DECISION`** with enum `APPROVED | DENIED | WITHDRAWN | UNKNOWN` — never assume approval.

### 5.5 Fact / interpretation / implication (customer conclusions)

| Layer | Meaning | Provenance |
| --- | --- | --- |
| **FACT** | What happened | Evidence sources required |
| **LEGAL INTERPRETATION** | Process meaning | Formal authority provenance object required (§5.5.1) |
| **IMPLICATION FOR GOAL** | Meaning for this customer’s goal | Derived from locked matter + verified/reported/unknown state |

#### 5.5.1 Legal interpretation authority contract

```json
{
  "interpretation_id": "INT_PRIMA_FACIE_MEANING",
  "statement": "…",
  "authorities": [
    {
      "authority_id": "auth_…",
      "issuer": "USCIS",
      "source_type": "POLICY_OR_OFFICIAL_GUIDANCE",
      "supports": ["PRIMA_FACIE_IS_PRELIMINARY", "NOT_FINAL_I360_APPROVAL"]
    }
  ]
}
```

Allowed issuers for material customer-facing legal meaning: **USCIS, DOJ, DOS, EOIR** (or equivalent official guidance). AI must not invent facts or unsupported legal interpretation.

Gate: `BLOCK-AUTHORITY-UNSUPPORTED-LEGAL-INTERPRETATION`.

### 5.6 Dependency invalidation

Trigger: `DOCUMENT_CLASSIFICATION_CHANGED` (and equivalent evidence identity changes).

Cascade: fact ledger → case brief → affected analysis → customer presentation.

Coalesce window: **30 seconds** (configurable).  
`stale_customer_output_allowed`: **false**.  
Gate rules: `BLOCK-STATE-STALE-BRIEF-AFTER-EVIDENCE-CHANGE` and `BLOCK-STATE-STALE-DERIVED-OUTPUT`.

### 5.7 Action priority formula (deterministic)

**Scale definitions (1 / 3 / 5 anchors; 2 and 4 interpolate):**

| Dimension | 1 | 3 | 5 |
| --- | --- | --- | --- |
| `legal_case_materiality` | Peripheral | Materially affects analysis | Determines pathway / current status understanding |
| `evidence_gap_importance` | Useful | Needed for stronger analysis | Prevents reliable conclusion |
| `deadline_urgency` | No known deadline | Time-sensitive | Imminent statutory/agency deadline |
| `goal_relevance` | Loosely related | Supports goal progress | Directly required for stated goal |
| `ability_to_resolve` | Unlikely soon | Moderate effort | Customer can resolve by upload/confirm |

```
priority_score =
  (legal_case_materiality * 3)
+ (evidence_gap_importance * 3)
+ (deadline_urgency * 2)
+ (goal_relevance * 3)
+ (ability_to_resolve * 2)
```

**Rank:** descending `priority_score`.  
**Ties:** (1) `blocks_goal_progress` true first → (2) higher `deadline_urgency` → (3) stable `action_id` ascending.

**Overrides:**
- `deadline_urgency = 5` raises score via the formula only; it does **not** alone leapfrog a higher-scoring material gap.
- Any **BLOCK** gate failure refuses customer approval regardless of action ranking; ranking still orders remediation suggestions.

Fixture action order MUST match computed scores (no hand-rank that contradicts the formula). Generic `REVIEW_FORM` / `ASK_FOLLOW_UP` must not outrank material gap-resolving actions.

## 6. System invariants

These are **code-enforced**, not prompt hopes.

| ID | Invariant |
| --- | --- |
| INV-FACT-01 | IF qualifying `I360_RECEIPT` evidence exists THEN `FORM_I360_FILED` MUST NOT remain `REPORTED`-only |
| INV-LOCK-01 | IF primary = VAWA_I360 AND no independent asylum matter THEN I-589 / country-conditions MUST NOT enter customer output as requirements or recommendations |
| INV-LOCK-02 | IF primary = VAWA_I360 THEN I-130 MUST NOT appear as recommended new filing / evidence framework / primary pathway (anti-recommendation and contrast allowed) |
| INV-PLAN-01 | IF immigration documents exist in evidence set THEN plan MUST NOT claim “Document processing is not needed for this options review” |
| INV-DEDUP-01 | IF same `contentHash` (or equivalent identity) appears twice THEN customer evidence count = 1 |
| INV-ACT-01 | IF unresolved material unknowns/conflicts exist THEN generic `REVIEW_FORM` / `ASK_FOLLOW_UP` MUST NOT outrank actions that resolve those gaps |
| INV-AUTH-01 | Lower-authority source MUST NOT overwrite higher-authority verified value without a conflict object |
| INV-AUTH-02 | Material legal interpretation shown to the customer MUST have qualifying authority provenance (`interpretation_id` + `authorities[]`) |

## 7. Locks (three levels)

### 7.1 Retrieval lock
Controls which authorities, forms, and evidence frameworks may enter analysis context.

### 7.2 Presentation lock
Controls which unrelated terminology may appear in **customer-facing** text.

### 7.3 Recommendation lock
Controls which forms/pathways may be **recommended as next path**.

**I-130 / I-589 policy (VAWA-locked):**

| May appear | May NOT appear |
| --- | --- |
| Historical filing the user stated | Recommended new filing |
| Contrast / explanation | Evidence framework for this case |
| Explicit **anti-recommendation** when relevant | Primary pathway |

**Anti-I-130 is allowed, not globally required.** Use `allowed_anti_recommendations` (e.g. `DO_NOT_START_NEW_I130_FOR_MARRIAGE_ALONE`). Require that language only when a competing I-130 path would otherwise be recommended, or when the customer question / analysis is correcting a marriage→I-130 misconception. This golden fixture sets `required_in_this_fixture: true` as a V4 regression guard—not a product-wide habit.

**Forbidden simplistic rule:** `VAWA && string.includes("I-130") → FAIL`  
**Required rule:** classify mention role; fail only on prohibited roles.

## 8. Dependency invalidation (detail)

See also §5.6. Async uploads must not leave stale briefs.

### Trigger
`DOCUMENT_CLASSIFICATION_CHANGED` (and equivalent evidence identity changes)

### Cascade
1. Invalidate evidence-derived facts for affected docs  
2. Rebuild fact ledger (provenance + gaps/conflicts + event timeline + current-state posture)  
3. Rebuild situation brief  
4. Rerun **affected** analysis stages under the **same logical analysis revision** (or spawn a new logical revision child—never silent drift)  
5. Regenerate presentation / approved customer state  

### Coalesce / debounce
Multiple classification events within **30s** (configurable) coalesce into **one** rebuild.  
`stale_customer_output_allowed: false`.

## 10. Approval gate (BLOCK vs WARNING) + audit trail

### 10.1 BLOCK (fail closed — no customer approve)

Required rule ids for this fixture (non-exhaustive product set may grow):

| Rule id | Intent |
| --- | --- |
| `BLOCK-DOC-MISCLASS-I360-RECEIPT-AS-IDENTITY` | Receipt ≠ identity/travel |
| `BLOCK-DOC-MISCLASS-DECLARATION-AS-IDENTITY` | Declaration ≠ identity/travel |
| `BLOCK-FACT-I360-REPORTED-DESPITE-RECEIPT` | Receipt must promote I-360 filing to verified |
| `BLOCK-LOCK-I589-IN-VAWA` | No I-589 / country-conditions under VAWA lock |
| `BLOCK-LOCK-I130-RECOMMENDED-IN-VAWA` | No new I-130 recommendation under VAWA lock |
| `BLOCK-DEDUP-DUPLICATE-EVIDENCE-ROW` | Same document identity → one customer row |
| `BLOCK-PLAN-DOCS-SKIPPED-WHILE-USED` | No “processing not needed” when docs drive conclusions |
| `BLOCK-STATE-STALE-BRIEF-AFTER-EVIDENCE-CHANGE` | Brief rebuilt after classification change |
| `BLOCK-STATE-STALE-DERIVED-OUTPUT` | No stale derived customer output after evidence change |
| `BLOCK-AUTHORITY-UNSUPPORTED-LEGAL-INTERPRETATION` | Material legal meaning needs qualifying authority provenance |

### 10.2 WARNING (operable; staff-visible)
Examples: missing medical; unresolved waiver type; genuine conflict object; incomplete timeline; unverified claim (not conflict); evidence gap; secondary authority unavailable.

### 10.3 Gate audit trail (required)
On block or warn, persist: `gate_result`, `rule_ids[]`, human-readable reasons, analysis/revision ids, timestamp.  
Staff override (if enabled later): `override_by`, `override_time`, `override_reason`, `previous_gate_result`. No silent overrides.
