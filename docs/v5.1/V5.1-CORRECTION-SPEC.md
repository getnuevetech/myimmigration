## 1. Purpose

V5 delivered the correct **architecture** (situation brief → case-type lock → six-section customer presentation → printable report). The six-page VAWA review showed the **customer shell is ahead of document → fact → action integrity**.

V5.1 does **not** redesign the UI. It makes the pipeline feeding that UI **correct, stale-proof, deduplicated, isolated, gated, and operationally reliable**.

## 5. Core data model requirements

### 5.1 Fact with provenance

Every ledger fact MUST carry explicit provenance:

```json
{
  "fact_id": "FORM_I360_FILED",
  "status": "VERIFIED",
  "value": true,
  "sources": [
    {
      "source_type": "DOCUMENT",
      "document_id": "doc_…",
      "document_type": "uscis_i360_receipt_notice",
      "field": "form_number",
      "authority_rank": "USCIS_GOVERNMENT_DOCUMENT"
    }
  ],
  "superseded_by": null,
  "as_of": "ISO-8601"
}
```

Customer “Verified from your documents” MUST be traceable to at least one DOCUMENT source.

### 5.2 Evidence authority hierarchy (highest → lowest)

1. USCIS / government document  
2. Filed form / official receipt  
3. Professional record  
4. Customer-uploaded supporting document  
5. Customer statement  
6. AI inference  

When sources disagree, **do not silently pick**. Create a **conflict** (see §5.3). Higher authority wins for `VERIFIED` value; lower authority may remain as `REPORTED` alongside.

### 5.3 Conflict objects

Conflicts are first-class and connect evidence → action:

```json
{
  "conflict_id": "conf_…",
  "subject": "I485_STATUS",
  "source_a": { "type": "USER_STATEMENT", "value": "APPROVED" },
  "source_b": { "type": "USCIS_DOCUMENT", "value": "RECEIPT_ONLY" },
  "severity": "WARNING",
  "resolution_status": "UNRESOLVED",
  "required_action": "UPLOAD_I485_DECISION_NOTICE"
}
```

Chain: **evidence → conflict → unknown/gap → ranked action**.

### 5.4 Superseded facts

Immigration timelines evolve. Older facts may remain **true historically** but be **superseded** for “current posture.”

Example I-360 chain:

`RECEIPT → PRIMA_FACIE → RFE → RFE_RESPONSE → APPROVAL`

Requirements:
- `superseded_by` / `supersedes` links on facts/events  
- Customer “current process” uses the **latest non-superseded** posture  
- Historical events remain visible in timeline / staff audit  

### 5.5 Fact / interpretation / implication (customer conclusions)

Every material customer conclusion SHOULD separate:

| Layer | Meaning | Example |
| --- | --- | --- |
| **FACT** | What happened (evidence-backed) | USCIS issued a Prima Facie Determination |
| **LEGAL INTERPRETATION** | What that means in process terms | Preliminary positive finding; not final I-360 approval; not a green card |
| **IMPLICATION FOR GOAL** | What it means for *this* customer’s goal | Green-card path still depends on related adjustment status/eligibility |

AI may draft interpretation/implication **only** from locked brief + scoped authority; it must not invent facts.

## 6. System invariants

These are **code-enforced**, not prompt hopes.

| ID | Invariant |
| --- | --- |
| INV-FACT-01 | IF qualifying `I360_RECEIPT` evidence exists THEN `FORM_I360_FILED` MUST NOT remain `REPORTED`-only |
| INV-LOCK-01 | IF primary = VAWA_I360 AND no independent asylum matter THEN I-589 / country-conditions MUST NOT enter customer output as requirements or recommendations |
| INV-LOCK-02 | IF primary = VAWA_I360 THEN I-130 MUST NOT appear as recommended new filing / evidence framework / primary pathway (anti-recommendation and contrast allowed) |
| INV-PLAN-01 | IF immigration documents exist in evidence set THEN plan MUST NOT claim “Document processing is not needed for this options review” |
| INV-DEDUP-01 | IF same `contentHash` (or equivalent identity) appears twice THEN customer evidence count = 1 |
| INV-ACT-01 | IF unresolved material unknowns/conflicts exist THEN generic `REVIEW_FORM` / `ASK_FOLLOW_UP` MUST NOT outrank actions that resolve those gaps |
| INV-AUTH-01 | Lower-authority source MUST NOT overwrite higher-authority verified value without a conflict object |

## 7. Locks (three levels)

### 7.1 Retrieval lock
Controls which authorities, forms, and evidence frameworks may enter analysis context.

### 7.2 Presentation lock
Controls which unrelated terminology may appear in **customer-facing** text.

### 7.3 Recommendation lock
Controls which forms/pathways may be **recommended as next path**.

**I-130 / I-589 policy (VAWA-locked):**

| May appear | May NOT appear |
| --- | --- |
| Historical filing the user stated | Recommended new filing |
| Contrast / explanation | Evidence framework for this case |
| Explicit **anti-recommendation** (“do not start a new I-130”) | Primary pathway |

**Forbidden simplistic rule:** `VAWA && string.includes("I-130") → FAIL`  
**Required rule:** classify mention role; fail only on prohibited roles.

## 8. Dependency invalidation

Async uploads must not leave stale briefs.

### Trigger
`DOCUMENT_CLASSIFICATION_CHANGED` (and equivalent evidence identity changes)

### Cascade
1. Invalidate evidence-derived facts for affected docs  
2. Rebuild fact ledger (provenance + conflicts + supersession)  
3. Rebuild situation brief  
4. Rerun **affected** analysis stages under the **same logical analysis revision** (or spawn a new logical revision child—never silent drift)  
5. Regenerate presentation / approved customer state  

### Coalesce / debounce
Multiple classification events within a short window (recommended **30s**, configurable) coalesce into **one** rebuild. No “hope the next manual re-analysis catches it.”

## 9. Action priority (deterministic inputs)

Phase D ranks actions by unresolved material facts/conflicts, using explicit dimensions (not opaque model prose):

```
priority ≈ Legal/Case Materiality
         × Evidence Gap Importance
         × Deadline Urgency
         × Goal Relevance
         × Ability To Resolve
```

Internal scores need not be shown to customers. They MUST explain why “Upload I-485 receipt” beats “Review Form I-360” for the golden VAWA case.

Golden expected order: see `next_actions_ordered` in [`golden-vawa-prima-facie.json`](./golden-vawa-prima-facie.json).

## 10. Approval gate (BLOCK vs WARNING) + audit trail

### 10.1 BLOCK (fail closed — no customer approve)
Examples:
- I-360 receipt classified as identity/travel  
- Declaration classified as identity/travel  
- I-360 filing remains reported despite qualifying receipt  
- Unrelated I-589 / I-130 **recommendation** under VAWA lock  
- Duplicate evidence rows for same document identity  
- Contradictory primary matter classification  
- Conclusions drawn while required document processing skipped  

### 10.2 WARNING (operable; staff-visible)
Examples:
- Missing medical  
- Unresolved waiver type  
- Customer recollection conflicts with document (conflict object)  
- Incomplete timeline  
- Secondary authority unavailable  

### 10.3 Gate audit trail (required)
On block or warn, persist:

- `gate_result` (`BLOCK` | `WARNING` | `PASS`)  
- `rule_ids[]` (e.g. `BLOCK-DOC-002`)  
- human-readable reasons  
- analysis / revision ids  
- timestamp  

On staff override (if enabled later):

- `override_by`, `override_time`, `override_reason`, `previous_gate_result`  

No silent overrides.

## 11. Reliability ceilings (Phase F targets)

Operational targets for a **single user-requested analysis** (adjust only with product approval):

| Metric | Ceiling |
| --- | --- |
| Logical analyses per user request | **1** |
| Max model attempts per stage | **2** |
| Max fallback models per stage | **1** |
| Max retries for malformed structured output | **1** |
| Uncaught model failures reaching customer output | **0** |
| Duplicate concurrent logical analyses for same revision | **0** |

Also define and measure (baselines set in Phase F write-up):
- expected analysis latency  
- max total model calls per logical analysis  
- success rate  
- token/cost envelope  

**Logical analysis ID** owns: retries, parse failures, fallbacks, child calls, and the customer-visible revision pointer.

## 13. Phase scopes (implementation after approval)

### F — Orchestration reliability
Root-cause failed-call / multi-run storm; implement logical analysis ID; enforce ceilings; admin diagnostics.

### A — Classification + dedupe
Trace classifier vs renderer; fix wrong layer; dedupe by content hash / file identity; plan-honesty copy when docs present.

### B — Fact ledger + invalidation
Provenance; hierarchy; conflicts; superseded; rebuild on classification change with debounce.

### C — Three locks
Retrieval / presentation / recommendation isolation with role-aware I-130/I-589 rules.

### E — Approval gate
BLOCK/WARNING evaluation before customer-facing approve; full audit trail.

### D — Action ranking
Deterministic priority inputs from unknowns/conflicts; demote generic form review.

### G — Fixture pack (~8–12) with positive **and** negative isolation tests

| Case | Must allow | Must forbid |
| --- | --- | --- |
| VAWA I-360 + pending I-485 | I-360/I-485 framing | I-130 recommend; I-589 country conditions |
| Marriage I-130 / I-485 | I-130 as pathway | Suppressing I-130 globally |
| Asylum I-589 | I-589 / country conditions when locked | — |
| VAWA (neg) | — | I-589 country conditions |
| RFE / NOID / EAD / N-400 / consular / AOS w/o petition / court notice | case-appropriate | cross-contamination |

Every intelligence change runs the **full pack**.
